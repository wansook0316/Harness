# Synthesis: 세 방법론의 관계와 스킬 설계 원칙

## 1. 세 방법론의 관계도

```
┌──────────────────────────────────────────────────────┐
│            Agentic Engineering (상위 패러다임)          │
│   "인간이 오케스트레이션, 에이전트가 실행"                │
│                                                       │
│   ┌───────────────┐    ┌────────────────────────┐    │
│   │      SDD      │    │  Harness Engineering   │    │
│   │   (무엇을)     │───▶│  (어떻게 제어할 것인가)   │    │
│   │  명세 = 진실    │    │  Inform + Verify       │    │
│   │  의도의 정형화   │    │  + Correct             │    │
│   └───────────────┘    └────────────────────────┘    │
│              │                      │                 │
│              ▼                      ▼                 │
│   ┌──────────────────────────────────────────────┐   │
│   │        Context Engineering (기반 기술)          │   │
│   │   "모델이 보는 것을 큐레이션하여                   │   │
│   │    더 나은 결과를 얻는 것"                        │   │
│   └──────────────────────────────────────────────┘   │
│                        │                              │
│                        ▼                              │
│   ┌──────────────────────────────────────────────┐   │
│   │       Cognitive Debt (핵심 리스크)               │   │
│   │   "속도가 이해를 초과할 때의 부채"                  │   │
│   └──────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────┘
```

### 관계 요약
- **SDD**는 "무엇을 만들 것인가"의 의도를 정형화하는 방법론
- **Harness Engineering**은 "에이전트를 어떻게 제어할 것인가"의 시스템 설계
- **Agentic Engineering**은 이 모든 것을 아우르는 상위 패러다임
- **Context Engineering**은 세 방법론 모두의 기반 기술
- **Cognitive Debt**는 이 모든 방법론이 해결하려는 핵심 리스크

## 2. 하네스 진단 프레임워크

### 핵심 질문

> **AI가 이 프로젝트 안에서 활동하기 좋은 환경인가?**

이 질문을 7개 그룹, 33개 세부 항목으로 분해한다.

---

### G1. Product Context — 서비스 정체성
> 에이전트가 "무엇을 위한" 코드를 작성하는지 이해하는가?

에이전트는 기술적으로 완벽하지만 제품적으로 틀린 코드를 만들 수 있다.
서비스의 정체성이 명문화되어 있지 않으면, 에이전트는 "누구를 위해, 왜" 만드는지 모른 채 코드를 생성한다.
(BMAD 방법론의 Product Brief 워크플로우 참고)

| ID | 진단 항목 | 판단 기준 |
|----|----------|----------|
| P1 | **서비스가 해결하는 핵심 문제가 정의되어 있는가?** | "왜 이 서비스가 존재하는가?" 현재 대안의 한계, 우리의 차별점이 명문화 |
| P2 | **타겟 사용자가 구체적으로 정의되어 있는가?** | 1차/2차 페르소나, 사용자 시나리오. "모든 사람"이 아닌 구체적 대상 |
| P3 | **서비스 철학/비전이 명문화되어 있는가?** | 제품 원칙, 디자인 철학, 핵심 가치. 기능 결정의 나침반 역할 |
| P4 | **규모와 단계가 정의되어 있는가?** | 현재 사용자 수, 목표 규모, 현재 단계(MVP/Growth/Scale). 규모에 따라 기술 결정이 달라진다 |
| P5 | **성공 지표가 정의되어 있는가?** | 사용자 성공 지표 + 비즈니스 지표. 측정 가능한 KPI |
| P6 | **현재 스코프 경계가 명확한가?** | "지금 만드는 것"과 "나중에 만들 것"의 경계. 에이전트의 과잉 구현 방지 |

### G2. Foundation — 환경 재현성
> 에이전트가 이 프로젝트를 실행할 수 있는가? (모든 검증의 전제 조건)

| ID | 진단 항목 | 판단 기준 |
|----|----------|----------|
| F1 | **빌드/실행 환경이 즉시 재현 가능한가?** | devcontainer, Docker, Nix 등 1-command setup 존재 |
| F2 | **의존성이 고정되어 있는가?** | lock file(package-lock, Pipfile.lock, go.sum 등) 존재 및 최신 |
| F3 | **환경 변수/시크릿이 안전하게 관리되는가?** | .env.example 존재, 실제 키 미노출, 로컬 테스트키 문서화 |

### G3. Entry & Navigation — 진입과 탐색
> 에이전트가 프로젝트에 착지한 직후 길을 찾을 수 있는가?

| ID | 진단 항목 | 판단 기준 |
|----|----------|----------|
| E1 | **AI 진입점이 존재하는가?** | CLAUDE.md / AGENTS.md / GEMINI.md 등 에이전트별 규칙 파일 |
| E2 | **깊이별 정보가 계층적으로 구성되어 있는가?** | 진입점 → 모듈별 README → 코드 내 인터페이스. 지도(map)인가, 매뉴얼인가? |
| E3 | **Context 문서가 최소한으로 유지되는가?** | 구조+인터페이스만으로 의도가 파악 가능한 수준. 문서가 코드의 보충이지 대체가 아닌 상태 |
| E4 | **프로젝트 핵심 원칙이 명문화되어 있는가?** | Constitution 또는 이에 준하는 문서. 스택, 네이밍, 허용/금지 규칙 |
| E5 | **도메인 개념이 정리되어 있는가?** | 유비쿼터스 언어 사전(glossary), 도메인 모델 다이어그램 |
| E6 | **금지 규칙이 명시되어 있는가?** | "하지 마라" 목록. 에이전트는 금지 규칙이 없으면 반드시 한다 |

### G4. Architecture & Structure — 구조와 확장성
> 프로젝트 구조 자체가 에이전트의 실수를 방지하는가?

| ID | 진단 항목 | 판단 기준 |
|----|----------|----------|
| A1 | **프로젝트 구조가 확장 가능하고 명확한가?** | 모듈 경계가 분명, 책임이 분리, 새 기능 추가 시 위치가 자명 |
| A2 | **이상적 코드 구조를 초기에 잡았는가?** | TDD, 클린 아키텍처 등. 코드 생성 비용이 싸진 만큼 이상적 구조의 선행 투자가 가능 |
| A3 | **기술 스택이 확장 가능하고 관리 가능한가?** | 언어/프레임워크/아키텍처가 장기 유지보수에 적합하며, harness-friendly한가 |
| A4 | **의존성 레이어가 정의되고 강제되는가?** | Types→Config→Repo→Service→Runtime→UI 등 방향성 있는 의존 흐름 |
| A5 | **에러 핸들링/로깅 컨벤션이 통일되어 있는가?** | 일관된 패턴이 없으면 에이전트가 매번 다른 방식으로 생성 |
| A6 | **디자인 철학이 있는가?** (UI 프로젝트) | 디자인 시스템, 컴포넌트 규칙, 접근성 기준 |
| A7 | **타입 시스템이 활용되고 있는가?** | strict mode, 타입 커버리지. 컴파일 타임 검증 = 가장 비용 효율적 검증 |

### G5. Verification & Quality Gate — 검증과 품질 관문
> 에이전트의 산출물을 자동으로 검증할 수 있는가?

| ID | 진단 항목 | 판단 기준 |
|----|----------|----------|
| V1 | **테스트 가능한가?** | 단위테스트 + E2E 테스트 인프라 존재 |
| V2 | **코드 퀄리티 유지 장치가 있는가?** | 린터, 포매터, 아키텍처 위반 시 빌드 에러 (ArchUnit, dependency-cruiser 등) |
| V3 | **CI에서 독립적 리뷰가 가능한가?** | PR 단위로 자동 검증 → 피드백 → 반영하는 루프 |
| V4 | **pre-commit hook이 설정되어 있는가?** | 커밋 전 1차 관문. 포맷, 린트, 타입 체크 등 |

### G6. Specification & Documentation — 명세와 문서
> 의도가 정형화되어 있고, 문서가 코드와 함께 살아 있는가?

| ID | 진단 항목 | 판단 기준 |
|----|----------|----------|
| S1 | **스펙 문서가 제1문서로 취급되는가?** | 명세 → 구현 흐름이 있고, 관리 룰이 존재 |
| S2 | **문서의 신선도가 유지되는가?** | 문서-코드 괴리를 감지하는 시스템 (CI 체크, 주기적 검증 등) |
| S3 | **API 계약이 명세화되어 있는가?** | OpenAPI, GraphQL schema 등 기계 판독 가능한 형태 |
| S4 | **ADR(Architecture Decision Records)이 관리되는가?** | "왜"의 기록. 인지적 부채 직접 방지 |

### G7. Operations & Maintenance — 운영과 유지
> 배포 후에도 하네스가 작동하는가?

| ID | 진단 항목 | 판단 기준 |
|----|----------|----------|
| O1 | **운영 모니터링 환경이 마련되었는가?** | 로그, 메트릭, 알럿. 에이전트가 observability 데이터에 접근 가능한가 |
| O2 | **가비지 컬렉터가 주기적으로 동작하는가?** | 문서 불일치, 아키텍처 위반, 미사용 코드를 정리하는 자동화 |
| O3 | **Git 워크플로우/브랜치 전략이 정의되어 있는가?** | 에이전트의 PR 생성/머지 방식이 명확 |
| O4 | **롤백 전략이 있는가?** | 에이전트가 만든 변경을 안전하게 되돌릴 수 있는가 |

### Fowler 3축과의 매핑

```
  ┌───────────────────────────────────────────────────┐
  │              G1. Product Context                   │
  │        (서비스 정체성 — 최상위 컨텍스트)              │
  └────────────────────────┬──────────────────────────┘
                           │
  ┌────────────────────────▼──────────────────────────┐
  │              G2. Foundation                        │
  │        (환경 재현성 — 기술적 전제 조건)               │
  └────────────────────────┬──────────────────────────┘
                           │
        ┌──────────────────┼──────────────────────┐
        │                  │                       │
   ┌────▼─────┐     ┌─────▼──────┐     ┌─────────▼──┐
   │  INFORM  │     │   VERIFY   │     │   CORRECT  │
   │          │     │            │     │            │
   │ G3 Entry │     │ G5 Quality │     │ G7 Ops     │
   │ G6 Spec  │     │    Gate    │     │            │
   │          │     │            │     │            │
   └────┬─────┘     └─────┬──────┘     └────────────┘
        │                 │
        └────────┬────────┘
                 │
          ┌──────▼──────┐
          │ G4 Archi-   │
          │ tecture     │
          │ (교차 영역)  │
          └─────────────┘
```

- **G1 (서비스)** 는 모든 그룹의 최상위 컨텍스트 — "왜, 누구를 위해"가 없으면 나머지가 방향을 잃는다
- **G2 (환경)** 은 세 축 모두의 기술적 전제 조건
- **Inform** ← G3 (진입과 탐색) + G6 (명세와 문서)
- **Verify** ← G5 (검증과 품질 관문)
- **Correct** ← G7 (운영과 유지)
- **G4 (구조)** 는 Inform과 Verify에 걸친다 — 좋은 구조 자체가 컨텍스트이면서 검증 장치

### 성숙도 모델

```
Level 0: Bare       하네스 없음. 에이전트에게 날것의 코드베이스
Level 1: Basic      진입점 + 기본 린터. 최소한의 가이드
Level 2: Guided     Constitution + CI + 구조적 테스트. 에이전트가 경계 안에서 작동
Level 3: Managed    SDD 워크플로우 + 자동 피드백 루프. 명세가 구현을 구동
Level 4: Optimized  자동 교정 + 인지 부채 관리. 하네스가 스스로 진화
```

#### 그룹별 성숙도 기준

| 그룹 | Level 0 | Level 1 | Level 2 | Level 3 | Level 4 |
|------|---------|---------|---------|---------|---------|
| **G1 Product** | 서비스 정의 없음 | 구두/암묵적 이해 | product brief + 페르소나 문서 | + 성공 지표 + 스코프 경계 명확 | + 지표 기반 자동 의사결정 |
| **G2 Foundation** | setup 절차 없음 | README에 수동 절차 | Docker/devcontainer | 1-command setup + seed data | 자동 환경 검증 + drift 감지 |
| **G3 Entry** | 진입점 없음 | AGENTS.md 존재 | + Constitution + glossary | + 계층적 문서 + 금지 규칙 | + 동적 컨텍스트 자동 주입 |
| **G4 Architecture** | 구조 없음 | 기본 디렉토리 구조 | + 레이어 정의 + 타입 strict | + 의존성 강제 + 컨벤션 통일 | + 자동 구조 검증 |
| **G5 Verification** | 테스트 없음 | 기본 린터 | + CI + pre-commit hook | + 커버리지 기준 + 아키텍처 테스트 | + 명세 기반 자동 검증 |
| **G6 Specification** | 문서 없음 | README | + API 명세 + ADR | + 스펙 제1문서 + 신선도 체크 | + 문서-코드 자동 동기화 |
| **G7 Operations** | 없음 | 수동 배포 | + 모니터링 + Git 전략 | + GC 에이전트 + 롤백 전략 | + 자기 수리 + 인지 부채 모니터링 |

## 3. 핵심 설계 원칙

### 3.1 "Map, not a Manual"
스킬이 생성하는 문서는 간결하고 구조화되어야 한다. 1,000줄짜리 AGENTS.md가 아니라 필요한 컨텍스트만 적시에 제공.

### 3.2 점진적 채택 (Progressive Adoption)
- Level 0에서 바로 Level 4로 갈 수 없다
- 세팅 스킬은 현재 레벨을 진단하고 **다음 레벨로의 구체적 단계**를 제안
- 소규모 버그에 SDD 전체를 적용하는 "슬레지해머" 접근 방지

### 3.3 도구 비종속 (Tool-Agnostic)
- Claude Code, Codex CLI, Gemini CLI 모두에서 작동
- 각 도구의 규칙 파일 형식 차이를 추상화
- cc-sdd의 크로스 플랫폼 접근 참고

### 3.4 Constitution 품질 우선
- 시니어 엔지니어의 판단이 필수
- 반복적 개선을 전제로 설계
- "프로젝트 DNA"를 정확히 인코딩

### 3.5 인지적 부채 인식
- 생성된 코드의 이해를 돕는 장치 포함
- "왜 이 결정이 내려졌는가"의 기록
- 팀 공유 이해 재구축 메커니즘
